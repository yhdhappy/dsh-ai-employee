# AI 员工插件｜技术架构设计文档

**版本：V0.2**
**日期：2026-09-14**
**目标宿主：DeepSeek Harness**
**文档状态：与产品设计 V0.3 同步更新，待评审冻结**

---

## 1. 技术目标

本插件需要在不重写 DeepSeek Harness 主体的前提下，为其增加一层"项目级 AI 员工协作系统"。

核心目标：

1. 接入不同 Agent / CLI；
2. 一个项目拥有独立 Bot 团队；
3. Bot 绑定 Agent、Model、Skill、Runtime；
4. Bot 可以私聊；
5. Bot 可以加入 Room；
6. Room 支持 `@` 路由和总顾问默认接管；
7. 项目可以拆 Module / Task；
8. 每个 Task 使用独立 Session；
9. Bot 之间通过 Handoff 交接；
10. **工作流由用户自定义**（不预设固定流程）；
11. 上下文、文件、记忆、权限按 Workspace 隔离；
12. 后续可运行在远程服务器。

# 3. 分层设计

## 3.1 UI Layer

负责：

- Workspace 切换
- Bot 列表
- Room（含任务卡片）
- Module / Task 树
- Session 列表
- Handoff
- Review
- 任务状态
- 用户审批
- Runtime 状态
- **首次使用引导（Onboarding）**
- **工作流配置界面**
- **通知中心**

UI 不直接调用 CLI Agent。

所有动作进入 Plugin Core。

## 3.2 Plugin Core

插件业务核心。

主要服务：

- **OnboardingService**（新增）
- **BotTemplateService**（新增）
- **WorkflowService**（新增）
- **NotificationService**（新增）
- WorkspaceService
- BotService
- RoomService
- ModuleService
- TaskService
- SessionService
- HandoffService
- ReviewService
- PermissionService
- RuntimeService
- AuditService

## 3.3 Orchestrator

负责任务调度。

它不等于"总顾问 Bot"。

总顾问是一个 Bot。

Orchestrator 是系统层调度器。

负责：

- 把 Room 消息路由给正确 Bot
- 根据 Task 状态触发下一阶段
- 根据**用户自定义工作流**触发下一棒
- 启动对应 Session
- 处理 Handoff
- 切换 DEV → REVIEW
- 处理失败 / 重试
- **触发通知**
- 等待用户审批
- 恢复中断任务

# 4. Provider Adapter Layer

这是借鉴 Paseo 思路的关键部分。

系统不能把逻辑写死到 Claude Code、Pi 或 Codex。

定义统一接口：

```ts
interface AgentProvider {
  id: string;
  name: string;

  probe(): Promise<ProviderHealth>;

  createSession(input: CreateSessionInput): Promise<ExternalSessionRef>;

  send(input: SendInput): Promise<AgentRunResult>;

  cancel(sessionId: string): Promise<void>;

  resume?(sessionId: string): Promise<void>;

  capabilities(): Promise<ProviderCapabilities>;
}
```

未来实现：

```text
providers/
├── harness/
├── pi/                  // V0.2 增补：Phase 0 唯一真实实现
├── claude-code/         // Phase 6 接入
├── codex/               // Phase 6 接入
├── opencode/            // 后续版本
└── ...
```

**V0.2 增补：Phase 0 验证时只接 PI Agent**作为首个外部 Provider，跑通最小主闭环。其他 Provider（Claude Code、Codex、OpenCode 等）按统一接口预留目录和类型签名，Phase 6 之前不实现实际 Adapter。

新增 Agent 时原则上只新增 Adapter，不修改 Bot、Task、Room 主逻辑。

# 6. Workspace

Workspace 是最强隔离边界。

```ts
type Workspace = {
  id: string;
  name: string;

  rootPath: string;
  memoryPath: string;      // V0.3 新增：项目记忆路径，默认 "<rootPath>/docs"

  status: "active" | "archived" | "deleted";  // 三态

  deletedAt?: string;       // 软删除时间
  deleteScheduledPurgeAt?: string;  // 30 天后真正清除

  ownerUserId: string;

  defaultAdvisorBotId?: string;

  reportPolicy:
    | "per_task"
    | "per_module"
    | "exception_only";

  // V0.3 新增：跨项目访问开关
  crossWorkspaceAccess: "disabled" | "enabled";
  // disabled: 默认禁止跨项目访问
  // enabled: 用户明确允许，可以指派 Bot 临时访问其他项目

  createdAt: string;
  updatedAt: string;
}
```

每个数据库查询都必须带：

`workspace_id`

禁止依赖前端传入的路径字符串作为唯一安全边界。

# 7. 文件访问安全

所有 Bot 文件访问必须经过 Workspace File Guard。

基本规则：

```text
Current Workspace Root
        │
        ├── READ   默认允许
        └── WRITE  根据 Bot 权限允许

Current Workspace <memoryPath>/（默认是 docs/）
        │
        ├── READ   默认允许
        └── WRITE  Bot 默认可以写（用于保存项目记忆）

Other Workspace
        │
        ├── READ   默认禁止
        └── WRITE  默认禁止
```

**V0.3 修改**：跨项目访问默认禁止，必须由用户在 Workspace 设置中开启 `crossWorkspaceAccess`。

**V0.3 新增**：`docs/`（或 `<memoryPath>/`）下的文件是项目记忆区域，Bot 默认可以读写。其他目录的写权限受 BotPermissions 控制。

用户临时授权（即使开启了跨项目访问，每次跨项目操作也需要授权）：

```ts
type CrossWorkspaceGrant = {
  id: string;
  subjectBotId: string;

  sourceWorkspaceId: string;
  targetWorkspaceId: string;

  access: "read" | "write";

  scope?: string[];

  reason: string;

  grantedByUserId: string;

  expiresAt?: string;
}
```

**所有跨项目访问必须记录审计信息**。

**V0.3 修改**：一个项目默认一个 Room（初期如此）。所有 Bot 默认都在这个 Room 里。

消息字段建议：

```ts
    | "task_card";         // V0.3 新增：任务卡片

  content: string;

  taskId?: string;
  handoffId?: string;
  taskCardId?: string;     // V0.3 新增
```

```ts
type TaskCard = {
  id: string;
  workspaceId: string;

  // 显示在 Room 右侧
```

# 9. Room 路由算法

伪逻辑：

```text
收到用户 Room 消息
        │
        ├─ mentions.length > 0
        │      ↓
        │   路由给 @Bot
        │
        └─ 没有 @
               ↓
      路由给 workspace.defaultAdvisorBot
        │
        ↓
   总顾问根据用户自定义工作流判断下一步
```

**V0.3 修改**：用户未 @ 时，总顾问接管。但总顾问需要参考项目的工作流定义，决定如何拆解任务、分派工作。

Bot 发消息时：

```text
@审核员 → 触发审核任务（按工作流）
@程序员 → 触发返工（按工作流）
@总顾问 → 汇报结果
```

注意：

Room 消息不应自动成为所有 Bot 的完整上下文。

只把与当前 Task 有关的最小片段注入对应 Session。

# 12. Task 状态机

```text
PLANNED
  ↓
READY
  ↓
DEVELOPING
  ↓
DEV_DONE
  ↓
REVIEWING
  ├───────────────┐
  ↓               │
PASS          CHANGES_REQ
  ↓               │
WAIT_OWNER         ↓
  ↓          DEVELOPING
DONE               │
                   └──→ REVIEWING
```

**V0.3 修改**：状态切换不一定按"程序员→审核员→总顾问"流程，而是按用户自定义工作流执行。但状态机的基本状态保持不变。

任何状态变化必须：

- 持久化
- 写审计日志
- 对应 Task ID
- 记录操作者

禁止只靠聊天文本判断任务状态。

# 14. Context Package

每个 Session 启动时不应读取整个项目。

应该动态生成 Task Context Package。

例如：

```text
Task Context Package
├── Bot Role
├── Workspace Rules
├── Product Constraints
├── Relevant Module Spec
├── Current Task
├── Acceptance Criteria
├── Previous Handoff
├── Selected Files
├── Relevant Decisions
└── Required Skills
```

这样避免上下文爆炸。

# 15. Handoff

Handoff 不是普通聊天消息。

它是结构化数据。

```ts
type Handoff = {
  id: string;
  workspaceId: string;
  taskId: string;

  fromBotId: string;
  toBotId: string;

  type:
    | "dev_to_review"
    | "review_to_dev"
    | "review_to_advisor"
    | "advisor_to_owner"
    | "task_to_task";

  summary: string;

  changedFiles: string[];
  generatedFiles: string[];

  verification: string[];

  knownIssues: string[];

  recommendations: string[];

  sourceSessionIds: string[];

  createdAt: string;
}
```

下一 Session 默认读取 Handoff，而不是读取前一个 Session 全文。

# 18. Bot 权限

建议使用 Capability 权限，不使用笼统"管理员"。

```ts
type BotPermissions = {
  canCreateBot: boolean;
  canModifyBot: boolean;
  canDeleteBot: false;                // 永远 false

  canCreateTask: boolean;
  canAssignTask: boolean;

  canReadWorkspaceFiles: boolean;
  canWriteWorkspaceFiles: boolean;

  canRequestCrossWorkspaceRead: boolean;

  canStartRuntime: boolean;

  canUseBrowser: boolean;
  canUseShell: boolean;

  // V0.3 新增
  canDeleteProject: false;            // 永远 false（即使是总顾问）
  canDeleteWorkspace: false;          // 永远 false
}
```

`canDeleteBot` 对所有 Bot 强制为 `false`。

**V0.3 新增**：`canDeleteProject` 和 `canDeleteWorkspace` 对所有 Bot 强制为 `false`。

删除项目、删除 Workspace 只能通过用户操作。

# 19. Runtime

Runtime 独立于 Bot 和 Provider。

```ts
type Runtime = {
  id: string;

  type:
    | "local"
    | "ssh"
    | "docker"
    | "cloud";

  status:
    | "online"
    | "offline"
    | "degraded";

  capabilities: {
    shell: boolean;
    browser: boolean;
    filesystem: boolean;
  }
}
```

后期支持：

```text
Bot → Provider → Runtime
```

例如：

```text
情报员
→ Pi Agent
→ 云服务器
```

即使用户 Mac 关机，任务仍继续。

# 20. Runtime 与调度状态必须分离

重要原则：

> Agent 进程不能成为系统唯一状态来源。

Task、Handoff、Room、Review 都必须持久化。

这样：

- CLI 崩溃
- 电脑重启
- Provider 断线
- 远程服务器断线

都可以恢复。

# 25. 汇报策略

Workspace 配置：

```text

per_module

```

# 26. Token / 上下文管理

核心原则：

1. Room 不作为全量上下文；
2. 一个 Task 默认独立 Session；
3. Review 独立 Session；
4. Session 结束生成 Handoff；
5. 永久记忆只存摘要；
6. Context Package 按需组装；
7. 大文件按相关性选择；
8. 不自动加载其他 Workspace；
9. **Bot 不预填 Skill（V0.3 新增）**。

建议后期增加：

- Token 预算
- Context 估算
- 自动压缩
- Snapshot
- Session rotation

# 28. 错误恢复与主动通知

### Provider crash

Session 标记 `failed`，Task 不丢失。

### Harness restart

从 SQLite 恢复 Workspace / Task / Session 状态。

### Remote runtime offline

Task → `BLOCKED`，Room 发状态消息，**触发用户通知**。

### Review timeout

可重试或换 Review Session。

### Agent 失控

用户可以：

- Cancel Session
- Pause Bot
- Pause Workspace

### V0.3 新增：主动通知

Bot 出问题时，**系统主动通知用户**：

触发场景：

- Bot 崩溃（连续 3 次失败）
- Session 卡死（超时无响应）
- Review 反复失败（连续 2 次不通过）
- 长时间无响应（超过设定阈值）
- Bot 给的答案明显异常
- 跨项目访问被拒绝

通知方式：

- 应用内通知
- 桌面通知（需要用户授权）
- 声音提示（可选）

通知由 NotificationService 统一处理。

### V0.3 增补：通知数据结构

每个通知带"跳转目标"信息，用户点击通知直接跳转到相关页面：

```ts
type Notification = {
  id: string;
  workspaceId: string;

  level: "urgent" | "important" | "normal";
  // urgent: 必须立即处理（Bot 崩溃、Session 卡死）
  // important: 重要但不阻塞（Review 反复失败、跨项目访问被拒绝）
  // normal: 状态变更（任务完成）

  title: string;
  body: string;

  // 跳转目标
  resourceType: "session" | "task" | "bot" | "workspace";
  resourceId: string;

  status: "unread" | "read";
  readAt?: string;

  createdAt: string;
  expiresAt: string;  // 创建时间 + 30 天
}
```

### 通知中心

- 用户在通知中心查看所有未过期通知
- 按时间分组：今天 / 昨天 / 更早
- 已读/未读区分显示（未读有标记）
- 点击通知跳转到对应 Session/Task 详情页
- 过期通知自动清理（30 天）

### 通知分级与打扰控制

- **紧急**：应用内 + 桌面 + 声音，全开
- **重要**：应用内 + 桌面，无声音
- **普通**：仅应用内通知中心，不主动弹窗

用户可在项目设置里调整通知级别偏好。

# 36. 当前最大风险

### 风险 1：过早接很多 Agent

Provider 数量不是核心价值。

先验证闭环。

### 风险 2：把 Room 当 Agent 上下文

会造成 Token 爆炸和信息污染。

### 风险 3：Bot 变成全局员工

会造成项目上下文交叉污染。

### 风险 4：用聊天记录代表系统状态

一旦进程崩溃，就无法恢复。

### 风险 5：让总顾问拥有删除权限

属于不必要的高风险权限。

### 风险 6：模块之间硬编码

后期无法替换 Provider、Runtime、Review 系统。

### 风险 7（V0.3 新增）：工作流设计过度复杂

如果工作流配置做得太复杂，普通用户玩不转，就违背了"用户主导、极简"的理念。

### 风险 8（V0.3 新增）：通知打扰太多

如果主动通知做得太频繁，会影响用户专注。需要分级（紧急/重要/普通）。

# 附录 B：项目记忆机制（V0.3 新增）

## B.1 设计目标

让 Bot 把"项目记忆"持久化在用户能直接看到的位置，用户可以用任意编辑器查看和编辑。

## B.2 存放位置

项目记忆统一放在 `<rootPath>/docs/` 目录下。

```text
我的项目/
├── docs/                  ← 项目记忆
│   ├── product.md         ← 产品设计文档
│   ├── architecture.md    ← 技术架构设计
│   ├── rules.md           ← 项目规则
│   ├── decisions.md       ← 决策记录
│   └── ...                ← 其他
├── src/                   ← 用户的源代码
└── ...
```

`docs/` 在项目创建时自动建立（空文件夹）。

## B.3 文件格式

统一使用 Markdown（`.md`）格式。

理由：

- 人和机器都看得懂
- VSCode、Typora 等编辑器原生支持
- 便于版本管理（Git diff 友好）

## B.4 写入机制

Bot 通过总顾问层 Tool 写入项目记忆：

```ts
workspace.write_memory({
  fileName: "product.md",     // 文件名（相对于 docs/）
  content: "..."              // Markdown 内容
})
```

写入规则：

- Bot 只能写到 `<rootPath>/docs/` 下
- 写到其他目录需要 `BotPermissions.canWriteWorkspaceFiles` 授权
- 写入动作记录审计日志

## B.5 读取机制

Bot 读取项目记忆有两种方式：

```ts
// 方式 1：读指定文件
workspace.read_memory({
  fileName: "product.md"
})

// 方式 2：列出 docs/ 下所有文件
workspace.list_memory()
```

Bot 启动 Session 时，会自动读取 `docs/` 下的关键文件（产品文档、技术架构、项目规则、决策记录）作为基础上下文。

## B.6 用户工具生成

用户可以用 Claude Code、Codex 桌面版等其他 Agent 工具生成文档，但**必须放到 `<rootPath>/docs/` 下**。

如果放到其他位置，Bot 默认读不到，需要用户告诉 Bot 去哪读。

## B.7 用户手动编辑

用户可以用任意文本编辑器（VSCode、TextEdit、Typora 等）打开 `docs/` 下的文件直接编辑。

Bot 下次读取时看到的是用户编辑后的最新版本。

## B.8 安全边界

- Bot 只能写 `<rootPath>/docs/` 下，不能写其他位置（除非有特殊权限）
- 用户随时可以查看 Bot 写的文件（透明）
- 用户随时可以编辑 Bot 写的文件
- 写入动作记录审计日志（actor、fileName、timestamp）

## B.9 与 Session 的关系

Session 启动时，系统会按需读取 `docs/` 下的相关文件作为 Context Package 的一部分（参见第 14 节）。

Session 结束后，Bot 生成的成果（包括 Handoff、决策、讨论结论）应**自动写入 `docs/` 下对应文件**，而不是堆在 Session 历史里。
