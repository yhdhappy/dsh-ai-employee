# AI 员工插件｜产品设计文档

**版本：V0.3**
**日期：2026-09-14**
**产品形态：DeepSeek Harness 插件**
**文档状态：在 V0.2 基础上补缺补漏，待评审冻结**

---

## 1. 产品定位

"AI 员工插件"是一套运行在 DeepSeek Harness 上的项目级 AI 团队系统。

它不是单纯的多 Agent 聊天界面，也不是把多个模型同时接进来就结束。它要解决的是：

> **让不同 Agent、不同模型、不同 Skill 驱动的 AI 员工，在同一个项目工作区中长期协作，并以任务、交接、审核和人工决策组成完整闭环。**

产品借鉴三个方向：

- **DeepSeek Harness**：作为插件宿主和 Agent 运行内核；
- **Paseo**：参考其多 Agent / CLI 接入和统一管理思路；
- **Grok Bot**：参考"长期 AI 员工、职责明确、持续工作、团队协作"的产品范式。

但本产品的核心区别是：

> **AI 员工不是全局存在，而是默认属于某一个项目工作区。**

用一句话讲就是：**给每个项目配一个 AI 团队**。

---

## 2. 核心产品原则

### 2.1 用户主导，不预设

产品提供基本结构（项目、员工、任务、协作），但**不替用户决定具体怎么用**。

- 用户决定项目里要几个员工、配什么角色；
- 用户决定员工能用什么 Skill；
- 用户决定任务怎么流转；
- 用户决定汇报节奏。

样板、流程都只是"起点"，用户可以随时改。

### 2.2 项目优先，而不是 Bot 优先

用户首先创建或选择一个项目工作区。

例如：

`/Users/.../AI_Workspace/Project_AI_Employee_Plugin`

该工作区就是这一项目的边界。

这个项目中的：

- Bot
- Room
- Module
- Task
- Session
- Handoff
- Memory
- 文件
- 代码
- 审核记录
- 决策记录

都默认只属于该项目。

### 2.3 每个项目拥有独立 AI 团队

项目 A 可以有：

- 总顾问
- 程序员
- 审核员
- 情报员

项目 B 可以完全不同：

- 产品经理
- 前端工程师
- 后端工程师
- 测试工程师
- 法务顾问

不同项目之间默认没有任何关系。

一个项目结束后，该项目中的 Bot 不再继续承担其他项目的工作，可以进入归档状态。

### 2.4 项目之间默认"零共享"

项目 B 中的 Bot 默认不能读取项目 A：

- 代码
- 文档
- Session
- Room
- Task
- Memory
- Handoff
- 决策记录

只有用户明确授权时，才允许跨项目访问。

跨项目权限原则：

1. 默认：无访问权限；
2. 用户在项目设置里自己决定：可指派某个 Bot 临时访问别的项目文件夹；
3. 所有跨项目访问必须记录审计信息。

一句话：

> **项目可以借鉴另一个项目的知识，但不能自动继承另一个项目的上下文和身份。**

## 3. 核心对象

整个产品采用以下结构：

```text
Workspace / 项目工作区
│
├── Room / 项目群聊
│
├── Bots / AI 员工
│   ├── 总顾问
│   │   └── Sessions
│   ├── 程序员
│   │   └── Sessions
│   ├── 审核员
│   │   └── Sessions
│   └── 其他 Bot
│
├── Modules / 功能模块
│   ├── Module 1
│   │   ├── Task 1
│   │   ├── Task 2
│   │   └── Task N
│   └── Module N
│
├── Handoffs / 交接记录
├── Files / 项目文件
├── Memory / 项目记忆
└── Decisions / 用户决策
```

## 4. Bot、Agent、Model、Skill、Runtime 必须分离

### Bot

代表一个长期 AI 员工。

例如：

- 总顾问
- 程序员
- 审核员
- 情报员

### Agent

Bot 所使用的执行器。

例如：

- DeepSeek Harness Agent
- Pi Agent
- Claude Code
- Codex CLI
- OpenCode
- 其他 CLI Agent

### Model

Agent 背后的模型。

用户可为不同的 Agent 选不同的模型。

### Skill

Bot 可以调用的专业能力。

每个 Bot 默认可以用所有已经安装好的 Skill，**不预填、不限制**。用户可以根据需要随时告诉某个 Bot 装哪个 Skill，或者告诉总顾问"帮某个 Bot 装 Skill"。

例如：

- Web Search
- GitHub Search
- 文档生成
- 去 AI 味
- 代码审核
- 浏览器自动化

### Runtime

Bot 真正运行的位置。

例如：

- 本机
- 远程服务器
- Docker
- 云主机

因此完整关系为：

```text
Bot
├── Role / 职责
├── Agent
├── Model
├── Skills（默认全部可用，按需调用）
├── Permissions
├── Runtime
└── Project Scope
```

## 5. 首次使用体验（Onboarding）

我们追求**极简**：用户第一次打开插件时不会被一堆引导淹没，而是可以立刻动手。

### 5.1 首次打开看到的画面

只有一个"创建项目"按钮和一行说明。

一行说明就是这句：

> **给每个项目配一个 AI 团队**

不再有示例项目、不再有引导弹窗、不再有"看一段演示"。

### 5.2 创建项目

用户点"创建项目"按钮，弹出一个窗口，只需要填两样东西：

1. **项目名**（必填）
2. **保存的文件夹**（用户选一个本地文件夹）

其他都用默认值，用户之后可以在项目设置里改。

项目建好后：

- 自动建一个空的 `docs/` 子文件夹，用来放项目记忆（产品文档、技术架构、项目规则等）；
- 项目里没有任何预置员工；
- 界面上显示四个"员工样板卡片"供用户挑选。

### 5.3 选样板建第一个员工

界面直接显示四个样板卡片：

- 📋 **总顾问**——负责理解需求、拆解任务、调度员工
- 💻 **程序员**——负责写代码、调试、测试
- ✅ **审核员**——负责检查代码、给出通过/不通过意见
- 🔍 **情报员**——负责搜索信息、整理报告

每个卡片上显示样板的名字和"能干啥、不能干啥"的简介。用户挑一个开始建。

### 5.4 用样板建员工

用户点样板卡片后，只需要：

1. 给员工起个名字（默认是样板的名字，比如"总顾问"）；
2. （可选）改一下"工作职责""工作边界"。

其他所有配置都从样板继承。用户建好员工后，随时可以编辑员工的所有配置。

### 5.5 加好第一个员工后

界面**直接进入跟这个员工的对话**，光标已经准备好。用户可以直接打字，比如：

> 帮我建一个程序员，负责写代码。

## 6. Bot 样板

产品内置四个样板，让用户快速建员工。用户可以用样板，也可以不基于样板自己从零建。

### 6.1 样板的灵活性

样板是**起点，不是锁死的**：

- 样板上的员工名字用户可以改（叫张三李四都行）；
- 样板里的"工作职责"用户可以增、删、改；
- 用户建好员工后，所有配置都能编辑。

### 6.2 四个样板的内容

#### 📋 总顾问样板

> **我是总顾问。我能：**
> - 听懂你的真实需求，把模糊的想法变成具体目标
> - 把大目标拆成小任务，分给合适的员工
> - 跟踪所有任务进度，协调员工之间的工作
> - 把技术问题翻译成人话，告诉你发生了什么、接下来怎么办
> - 保护项目边界，不擅自访问其他项目
>
> **我不能：**
> - 直接写代码
> - 删除任何员工
> - 跨项目偷看其他项目
> - 替你做不可逆的决定（比如删数据、发邮件）

#### 💻 程序员样板

> **我是程序员。我能：**
> - 根据任务写代码
> - 调试、运行测试、修复 bug
> - 加注释、写文档
> - 完成后写交接文档，交给审核员
>
> **我不能：**
> - 删项目里的文件（除非你明确同意）
> - 改其他项目的代码
> - 跳过测试直接交活

#### ✅ 审核员样板

> **我是审核员。我能：**
> - 检查代码是否符合任务要求
> - 检查测试是否齐全、是否都通过
> - 给出"通过"或"需修改"意见
> - 列出审核中发现的问题
>
> **我不能：**
> - 改代码
> - 跳过审核
> - 通过没测过的代码

#### 🔍 情报员样板

> **我是情报员。我能：**
> - 搜索网页、文档、新闻
> - 整理和分析信息
> - 写简明的报告
>
> **我不能：**
> - 写代码
> - 改文件
> - 访问其他项目

### 6.3 不止四个样板

如果用户想要更多角色（比如"测试员""法务顾问""设计师"），可以从零自己建一个员工，或者基于现有员工"另存为样板"。

## 7. Bot 创建和权限

### 7.1 三种创建方式

用户可以通过以下三种方式中的任何一种添加员工：

1. **界面创建**：从样板选一个，或者从零开始建；
2. **跟总顾问说**：用户告诉总顾问"帮我建一个程序员"，总顾问直接创建；
3. **跟员工私聊**：用户直接跟某个员工说"帮我再建一个测试员"。

### 7.2 Bot 也可以创建员工

任何一个 Bot 都可以按照用户的指挥添加、修改员工，**但不能删除员工**。

例如：

- 用户告诉总顾问"帮我建一个程序员"，总顾问直接创建；
- 用户告诉程序员"再建一个测试员"，程序员直接创建；
- 但任何 Bot 都不能删员工。

### 7.3 总顾问权限

总顾问可以在用户授权范围内：

- 创建 Bot
- 修改 Bot
- 修改职责
- 修改 Agent / Model
- 增减 Skill
- 调整工作范围
- 派发任务

总顾问不能：

- 删除 Bot
- 删除项目
- 擅自跨项目读取
- 擅自跨项目修改

### 7.4 删除员工：只有用户能执行

**任何 Bot 都没有权利删除员工，包括总顾问。**

删除员工永远只允许用户执行。这一条是死规矩，任何 Bot 都不得违反。

## 9. 私聊

点击任意 Bot，可以进入一对一私聊。

例如：

```text
用户 ↔ 总顾问
用户 ↔ 程序员
用户 ↔ 审核员
```

私聊不需要 `@`。

用户可以直接给某个 Bot 单独安排工作。

---

## 10. Room：项目群聊

### 10.1 一个项目一个 Room

每个项目只有一个 Room，**初期先这样**。所有员工默认都在这个 Room 里。

以后如果用户需要，再开发"多 Room"功能。

### 10.2 Room 的形态

Room 采用**群聊 + 任务卡片**混合形态：

- **左边**：消息流（像群聊），用户和员工发消息，能 @ 别人；
- **右边**：任务卡片和交接状态，让人一眼看到"谁干完了、交给谁了、下一步是谁"。

### 10.3 Room 的作用

Room 是**协调中心**，不是干活的地方。

- 谁负责
- 谁完成了
- 谁来审核
- 审核是否通过
- 是否需要返工
- 是否需要用户决策
- 下一步做什么

Room 不承载大量开发过程——员工真正干活是在自己的 Session 里。

### 10.4 Room 让用户一目了然

用户的核心价值是：**在 Room 里一眼看到交接链路**。

- 程序员完成任务 → Room 自动显示交接卡片 → @ 审核员
- 审核员审核 → Room 显示审核结果 → @ 总顾问
- 总顾问用人话汇报 → 用户看到汇报 → 决定下一步

用户不必读完所有聊天历史就能知道项目进展到哪了。

---

## 11. Room 的路由规则

### 11.1 用户 @ 某个 Bot

例如：

> @程序员，请完成 Task 3。

则直接交给程序员。

`@Bot` = 强制路由。

### 11.2 用户未 @

例如：

> 我想把登录模块重新做一下。

则默认由总顾问接管。

总顾问负责：

- 理解目标
- 判断需要哪些 Bot
- 拆解任务
- 分派工作
- 跟踪状态
- 汇总结果

### 11.3 Bot 之间可以 @

例如程序员完成任务后：

> @审核员，Task 3 已完成。修改了 4 个文件，测试 18/18 通过，请审核。

审核员收到后进入自己的 Review Session。

审核结束后：

> @总顾问，Task 3 审核未通过。发现 2 个问题，详见审核记录。

或：

> @总顾问，Task 3 审核通过。

Room 只显示"交接结果"，不显示大段执行过程。

## 12. Room 与 Session 的边界

这是本产品的核心交互规则之一。

### Room

用于：

- 谁负责
- 谁完成了
- 谁来审核
- 审核是否通过
- 是否需要返工
- 是否需要用户决策
- 下一步做什么

### Session

用于：

- 真正写代码
- 阅读项目文件
- 调试
- 搜索
- 测试
- 长上下文推理
- 生成文档
- 审核代码
- 修改实现

一句话：

> **Room 是会议室，Session 是员工真正干活的办公室。**

## 13. 工作流：用户自定义

任务在 Bot 之间怎么流转，**由用户自己定义**，不是系统预设的固定流程。

### 13.1 为什么需要自定义

不同项目的任务流转不一样：

- 开发项目：程序员 → 审核员 → 总顾问汇报
- 研究项目：情报员 → 审核员 → 总顾问汇报
- 运营项目：内容官 → 审核员 → 用户

V0.2 假设的"程序员 → 审核员 → 总顾问"只是众多流程中的一种，不是固定的。

### 13.2 工作流的最小单位

工作流由"步骤"组成，每个步骤指定：

- 谁来做（哪个 Bot）
- 完成后交给谁（下一个 Bot，或者用户）

### 13.3 两种定义方式

用户可以用**两种方式**定义工作流：

#### 方式 A：跟总顾问说（推荐）

用户用大白话告诉总顾问：

> 我要个流程：先让程序员干，干完交给审核员，审核员审核完你用人话告诉我。

总顾问帮用户建工作流。

#### 方式 B：界面配置

界面上有个表单，用户填：

- 步骤 1 是哪个 Bot
- 步骤 2 是哪个 Bot
- 步骤 3 是哪个 Bot（或者"用户"）

### 13.4 工作流的应用

工作流建好后，员工完成任务会自动触发下一步：

- 程序员完成 Task 1 → 自动交接给审核员
- 审核员完成审核 → 自动交接给总顾问
- 总顾问用人话汇报给用户

用户可以在工作流里随时插入"等用户决策"这样的步骤。

## 14. Module：功能模块

项目在产品和技术设计明确后，应拆成多个功能模块。

例如 AI 员工插件可能包括：

- Workspace 模块
- Bot 管理模块
- Agent Provider 模块
- Room 模块
- Task 模块
- Session 模块
- Handoff 模块
- 权限模块
- Runtime 模块

每个模块有明确：

- 目标
- 输入
- 输出
- 边界
- 接口
- 验收条件

模块之间通过标准接口连接，避免互相侵入。

---

## 15. Task：最小工作单元

一个 Module 可以拆成多个 Task。

例如：

```text
模块：Bot 管理

Task 1：Bot 数据结构
Task 2：Bot 创建接口
Task 3：Bot 编辑接口
Task 4：Bot 删除权限
Task 5：Bot 列表 UI
Task 6：Bot 详情 UI
...
```

每个 Task 是独立可执行、可审核、可验收的工作单元。

---

## 16. Task 与 Session 的关系

默认：

> **一个 Task 至少创建一个独立 Session。**

这样避免一个模块几十个任务全部堆在一个超长上下文里。

但 Task 和 Session 不应强制一对一。

一个复杂 Task 可以有：

- Dev Session 1
- Dev Session 2
- Debug Session
- Review Session
- Re-review Session

因此正确关系是：

> **Task 是工作单；Session 是完成这张工作单时使用的独立上下文容器。**

---

## 17. Handoff：任务交接

每个 Task 完成阶段都要生成结构化 Handoff。

例如程序员交接给审核员：

```text
Task：BOT-03

完成内容：
- 新增 Bot 创建接口
- 新增字段校验
- 增加 8 个测试

修改文件：
- src/bot/create.ts
- src/bot/schema.ts
- tests/bot/create.test.ts

验证：
- 8/8 PASS

已知风险：
- 尚未处理远程 Runtime

下一角色：
- 审核员
```

审核员不需要读取程序员全部聊天历史。

审核员首先读取：

1. Task 要求
2. Handoff
3. 代码 diff / 相关文件
4. 测试结果

必要时再查看原 Session。

## 18. 任务状态

每个 Task 必须有明确状态。

建议：

```text
PLANNED       已规划
READY         可开始
DEVELOPING    开发中
DEV_DONE      开发完成
REVIEWING     审核中
CHANGES_REQ   需要修改
RE_REVIEWING  再审核
PASS          审核通过
WAIT_OWNER    等待用户决策
DONE          完成
BLOCKED       阻塞
```

用户不需要记这些英文。

界面显示中文即可。

## 19. 用户汇报策略

总顾问不必每完成一个 Task 都打断用户。

### 19.1 三种策略

用户在**项目设置**里自己选一种：

#### 按 Task 汇报

每完成一个 Task，向用户汇报。

#### 按 Module 汇报

模块全部完成后，再一次性汇报。

#### 仅异常汇报（推荐默认）

正常情况自动继续，只有：

- 阻塞
- 审核反复失败
- 需要范围变更
- 需要权限
- 存在高风险
- 需要用户拍板

才打断用户。

### 19.2 异常永远升级

不管用户选哪种策略，异常情况永远允许升级：

- BLOCKED
- 权限不足
- 审核多次失败
- Scope 变化
- 安全风险
- 数据删除
- 外部发布

---

## 20. 总顾问向用户的汇报规则

必须"用人话"。

不应只说：

> CI failed because schema migration conflicted.

而应该说：

> 这个任务现在卡住了。原因是旧数据库结构和新结构冲突，如果继续直接改，可能会破坏已有数据。我的建议是先增加一个兼容迁移步骤，大约多一个小任务。你可以选择：A 先兼容旧数据；B 直接清空测试数据重新做。

总顾问负责把技术问题翻译成用户可以判断的决策。

## 21. 项目记忆

Bot 的记忆不是全局无限累积。

每个 Bot 的长期上下文和记忆默认只属于当前 Workspace。

### 21.1 记忆放在哪

**项目记忆统一放在项目文件夹下的 `docs/` 子文件夹里**。

例如：

```text
我的项目/
├── docs/                  ← 项目记忆都在这里
│   ├── product.md         ← 产品设计文档
│   ├── architecture.md    ← 技术架构设计
│   ├── rules.md           ← 项目规则
│   ├── decisions.md       ← 决策记录
│   └── ...                ← 其他
├── src/                   ← 你的源代码
└── ...
```

`docs/` 是项目建好后自动创建的。用户可以用任意文本编辑器（VSCode、Typora 等）直接打开看、编辑。

### 21.2 记忆的产生

项目记忆的产生有**两条路径**：

#### 路径 A：跟 Bot 讨论生成（推荐）

用户跟 Bot 一起讨论：

- 产品设计文档
- 技术架构设计
- 项目规则
- 决策记录
- 等等

讨论完成后，Bot 调用写入工具，**自动写到 `docs/` 下对应的 Markdown 文件**，比如：

- `docs/product.md`
- `docs/architecture.md`
- `docs/rules.md`
- `docs/decisions.md`

#### 路径 B：用户用其他工具生成

用户可以用 Claude Code、Codex 桌面版等其他 Agent 工具完成产品文档、技术文档设计。

生成的文档**必须放到项目文件夹下的 `docs/` 子文件夹里**，Bot 才能读到。

如果放到别处（比如直接放在项目根目录），Bot 读不到，需要用户告诉 Bot 去哪读。

### 21.3 记忆的分类

项目记忆包括但不限于：

- 项目规则（rules.md）
- 产品文档（product.md）
- 技术架构（architecture.md）
- 决策记录（decisions.md）
- 当前模块摘要
- 已完成任务摘要
- Bot 自己的角色规则

### 21.4 Session 结束后的处理

Session 结束后，不应把整个 Session 原样塞入永久记忆，而应生成摘要和 Handoff。

## 22. 跨项目访问

### 22.1 默认零共享

项目 A 的 Bot 默认**完全不能**访问项目 B 的任何内容。

### 22.2 用户授权

用户在**项目设置**里自己决定，是否允许跨项目访问。

如果允许，用户可以：

- 指派某个 Bot 临时访问另一个项目文件夹（比如"让情报员读一下项目 B 的产品文档"）；
- 指定访问范围（读 / 写）；
- 指定有效期。

### 22.3 审计

所有跨项目访问必须记录审计信息，包括：

- 谁访问的
- 访问了哪个项目
- 访问了什么内容
- 什么时候访问的

## 23. 异常处理

### 23.1 系统主动通知

Bot 出问题时，**系统主动通知用户**：

- Bot 崩溃
- Session 卡死
- Review 反复失败
- 长时间无响应
- Bot 给的答案明显异常

通知方式包括：

- 应用内通知
- 桌面通知
- 声音提示（可选）

用户第一时间知道发生了什么，可以介入。

### 23.2 用户随时可以查

用户也可以随时去"状态页"看：

- 每个 Bot 当前在干啥
- 每个 Task 当前状态
- 每个 Session 是否正常运行

### 23.3 用户可以介入

用户可以：

- Cancel Session（取消某个 Session）
- Pause Bot（暂停某个员工）
- Pause Workspace（暂停整个项目）
- 重启 Session
- 换 Bot 重试

### 23.4 通知中心

通知中心是用户查看和管理通知的地方。

- 通知列表**按时间分组**：今天 / 昨天 / 更早
- 通知分**已读/未读**，未读有明显标记
- 通知**保留 30 天**，过期自动清理
- 点击通知**直接跳转到相关 Session 或 Task 详情页**

### 23.5 通知分级

为了避免打扰用户，通知分三个级别：

- **紧急**：必须立即处理，比如 Bot 崩溃、Session 卡死。应用内+桌面+声音全部提示。
- **重要**：需要知道但不阻塞，比如 Review 反复失败、跨项目访问被拒绝。应用内+桌面提示，没有声音。
- **普通**：状态变更通知，比如任务完成。只在通知中心出现，不主动弹窗。

用户可以在项目设置里调整各项目偏好的通知级别。

## 24. 项目状态管理

项目有**三种状态**：

### 24.1 活跃（Active）

项目正在使用中，员工正常工作，可以加任务、加员工。

### 24.2 归档（Archived）

项目已经完成，或者用户暂时不想继续了，可以选择归档。

归档后：

- Bot 停止主动工作
- Routine 停止
- Session 只读
- Room 只读
- 文件保留
- 交接和决策保留
- 项目可重新激活

### 24.3 删除（Deleted）

归档后的项目如果不需要了，可以**彻底删除**。

**删除必须由用户自己操作**，任何 Bot 都不能删除项目。

删除是不可逆操作，系统会要求用户二次确认。

## 27. 产品成功标准

第一阶段成功，不是"接了多少模型"。

而是能完整完成：

> **用户建立一个项目 → 建立总顾问、程序员、审核员 → 用户自定义工作流 → 程序员独立 Session 开发 → Handoff → 审核员独立 Session 审核 → 不通过返工 / 通过 → 总顾问用人话汇报 → 用户决定下一步。**

如果这条主闭环稳定成立，产品模型就成立。
